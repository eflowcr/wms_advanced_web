Qué resuelve, y cuándo NO usarlo

Qué resuelve

Un botón cuyo único contenido visible es un icono. Para filas de tabla, barras de herramientas densas y cualquier lugar donde el texto no cabe.

No es una variante del Botón, y la razón es de tipos. En un componente único label tendría que ser opcional —sería redundante cuando hay texto— y entonces nada impide escribir <ewms-button icon="trash" />: compila, y no tiene nombre accesible. Siendo dos componentes, label es requerido en el tipo y ese botón no compila.

Hay una segunda razón, geométrica: un botón de texto Medium mide 40 px de alto con 16 px de padding horizontal; quitarle el texto deja una caja de ~50 px con un icono de 18 px flotando. El Icon Button es cuadrado. Son dos reglas de tamaño distintas.

Cuándo NO usarlo

  • Si hay lugar para texto, va texto. Un icono solo siempre es más ambiguo que una palabra. Este componente es para cuando la palabra no entra, no para cuando queda más prolijo.
  • Si navega, es un link, igual que con el Botón. Un botón que lleva a otra URL rompe abrir en pestaña nueva, copiar el enlace y el botón «atrás».
  • Si esperabas que el tooltip fuera el nombre, no lo es. El tooltip describe para quien ve; el nombre lo da aria-label, para todos. Van los dos.

El tercero es el caso que justifica que tooltip no se genere solo: label dice «Eliminar artículo» y tooltip agrega «(no se puede deshacer)». Derivarlo cerraría exactamente este caso.

Los dos miden exactamente lo mismo: el contenido se oculta con visibility y no con display, así que nada de al lado se mueve. En un control cuadrado eso se nota más que en uno de texto.

Variantes

Las mismas cuatro del Botón, con Ghost por defecto — no Primary. Este control vive en filas y toolbars, donde el énfasis correcto es el más bajo; un Primary por defecto llenaría cada fila de una tabla de cajas azules y arruinaría la jerarquía de la pantalla.

    @for (variant of variants; track variant.id) {
  • {{ variant.label }}
    • }

Los estados son idénticos a los del Botón —misma tabla, mismos tokens— y no se redefinen acá: los dos componentes comparten la implementación en button.types.ts. Dos APIs públicas, un solo estilo.

Matriz de estados

Renderizada de verdad. Disabled y Loading son entradas reales del componente; Hover y Focus no se pueden dejar quietos, así que cada celda recibe el mismo token que aplicaría su propia regla.

Disabled se pasa como atributo, no se pinta con una clase. Forzarlo por CSS dejaría a axe mirando un control habilitado con la paleta de deshabilitado, y el 1.38:1 del texto deshabilitado —que la WCAG exime justamente por estar deshabilitado— se reportaría como un fallo de contraste que el componente no tiene.

Tamaños

Tres, y cuadrados: las mismas alturas de control del sistema, usadas también como ancho.

    @for (sample of sizes(); track sample.size) {
  • {{ sample.label }} · {{ sample.box }} @if (sample.clearsTarget) { supera {{ minimumTarget }}×{{ minimumTarget }} } @else { por debajo de {{ minimumTarget }}×{{ minimumTarget }} }
    • }

Las medidas de arriba están leídas de la caja renderizada, y la comparación contra el mínimo de WCAG 2.2 §2.5.8 (Target Size, nivel AA) se calcula con ellas: las tres lo superan, Small incluido. Un número transcrito acá no demostraría ni que la caja es cuadrada ni que el criterio se cumple.

El icono usa el mapeo del Botón —sm (16 px) en Small, md (18 px) en Medium y Large— y no uno propio más grande, aunque sea el único contenido: los dos conviven en la misma barra de herramientas, y dos iconos de tamaño distinto uno al lado del otro se leen como un error.

Contrato para Angular

Entradas

Las siete de la tabla del bloque 3. Tres son input.required(): icon, label y tooltip. Requerido significa requerido en el tipo, no un input opcional con valor por defecto — un default vaciaría la garantía.

Salidas

Ninguna. Igual que el Botón, se escucha el (click) nativo, que burbujea desde el <button> interno; cuando el control está disabled o loading el componente detiene el evento antes de que salga.

La ficha del vault declara (click): EventEmitter<MouseEvent>. Gana el código: un output llamado click se superpone al evento nativo del mismo nombre y deja dos caminos para una sola cosa.

Accesibilidad

  • aria-label con el texto de label. El icono interno va aria-hidden: es decoración, el nombre lo da el label.
  • El tooltip no es el nombre accesible. Son dos cosas para dos públicos: el tooltip aparece al hover y al foco —quien navega con teclado puede no verlo, y en pantalla táctil el hover no existe—; el aria-label funciona para todos, siempre. Por eso van los dos.
  • Y por eso mismo el panel del tooltip va aria-hidden cuando repite el nombre: la directiva se aplica con [describes]="false", para que el lector de pantalla lo anuncie una sola vez.
  • En Loading conserva el foco: se deshabilita con aria-disabled y no con el atributo nativo, por la misma razón documentada en el Botón.
  • Anillo de foco visible con :focus-visible, en las cuatro variantes.

Errores comunes

  • Un icon button sin label es un botón mudo. En una fila de tabla con tres de ellos, quien usa lector de pantalla oye «botón, botón, botón». Acá no compila — es un error de build, no un acuerdo humano.
  • Poner variant="primary" en una tabla. El default es Ghost por diseño; si cada fila pide énfasis, ninguna lo tiene.
  • Escribir [ewmsTooltip] encima del componente. El componente ya aplica la directiva por dentro. La entrada se llama tooltip, a secas: el selector ya lleva el prefijo.
  • Suponer que el icono escala con el tamaño. No lo hace en Large: se queda en md, a propósito.

Bloques que no aplican

Ninguno: los ocho aplican a este componente.
